# F-06 — Instant-On standby must not burn the daily allowance

**Finding (REVIEW.1 §3, F-06).** v1 decided `up` from the number of concurrent
conntrack flows. The Xbox Series S ships with **Instant-On** as the default power
mode and holds persistent connections to Xbox Live while apparently switched off,
so a standby console clears any flow threshold. `engine.go` increments
`day.TUMinutes` on every tick where the state is `up`, so a console sitting in
standby all afternoon consumes the whole day's allowance and the kid arrives to
`blockedNoTime`. That is the most visible way this deployment could fail.

## What v2 measures instead

The signal is the console's **outbound byte rate**, compared against
`device.json` → `state.threshold_bytes_per_min`. `getState.sh` samples it, divides
by the elapsed time, and reports `up` above the threshold.

### The byte source: conntrack, not nft counters

The original v2 design put an nft named counter in a chain at
`hook forward priority -160`. **Measurement on the real router killed that design.**
This router runs fw4 with `flow_offloading_hw='1'` and a flowtable carrying
`flags offload` on a MediaTek PPE. Hardware-offloaded packets are forwarded in
silicon and never enter the CPU's netfilter forward hook, so the counter would have
seen only each flow's first packets and reported `down` during real gameplay. No
software hook rescues this — `netdev ingress` is bypassed for the same reason.

What does work is **conntrack byte accounting**. fw4 declares its flowtable with
`counter`, and Linux 6.6 feeds the hardware's per-flow MIB back into conntrack via
`nf_ct_acct_add()` on a ~1 Hz poll. Verified empirically on this SoC: 9 of 9
hardware-offloaded flows gained bytes over a 20 s window, none static. See
[PROGRESS.md](PROGRESS.md) "Check B" for the full evidence.

So the helper sums `/proc/net/nf_conntrack` byte counters for the console's
addresses, per direction, router-side, and returns one number per direction. This
has no nft table, no chain, no priority, no device names, nothing to survive an fw4
reload, and no package dependency.

**Trade-off:** conntrack is keyed on the console's **IP**, not its MAC, which gives
up the IPv6 coverage that motivated F-04. Safe for this deployment — the ISP
delegates no IPv6 — but it must be revisited if that ever changes. The *enforcement*
rule stays MAC-keyed and is unaffected.

**The console has two MACs.** Measured 2026-09-15: the console appears as
`d8:e2:df:92:a9:93` → `.172` on ethernet (static reservation) and
`d8:e2:df:92:a9:90` → `.169` on WiFi (dynamic lease). Whichever mechanism is used
must cover **both**, or the driver silently measures an interface the console is not
using. This is tracked as a correctness defect in [PROGRESS.md](PROGRESS.md).

## Calibration procedure

Requires the console present and the driver working (`./xbox.py selftest` green).

```
# 1. console in STANDBY (powered "off" but Instant-On), nobody touching it
./xbox.py calibrate --minutes 30 --interval 60 --label standby

# 2. console ACTIVELY in use — a game online, or a streaming app
./xbox.py calibrate --minutes 10 --interval 60 --label gaming

# 3. optional: console downloading a game update, nobody playing
./xbox.py calibrate --minutes 10 --interval 60 --label downloading
```

Samples are appended to `calibration.jsonl`. Each run prints
`n / min / median / max` in KB/min at the end.

Pick the threshold as: **comfortably above the standby maximum, comfortably below
the gaming minimum.** Geometric midpoint is a reasonable default:
`threshold ≈ sqrt(standby_max × gaming_min)`. Write it into `device.json` as
`state.threshold_bytes_per_min` (bytes, not KB).

If the two ranges overlap, the console is doing something in standby that looks
like use — check for a background download before lowering the threshold.

## Results

Shipped default until calibrated: **204800 bytes/min (200 KB/min)**.

### Measured 2026-09-15 (console on WiFi `phy0-ap0`, MAC `d8:e2:df:92:a9:90`, IP `.169`)

Outbound is the deciding metric. Each row is a real measurement against the live
console, using the per-flow conntrack accumulator described below.

| label | conntrack out | iwinfo out | inbound | verdict @ 200 KB/min |
|---|---|---|---|---|
| idle / dashboard | **20.8** KB/min | — | 23 KB/min | DOWN ✓ |
| downloading | **93.7** KB/min | 131.0 KB/min | 11.8 MB/min | DOWN ✓ |
| **gaming** (82 UDP flows, dport 22222) | **289.5** KB/min | 340.5 KB/min | — | **UP** ✓ |

**Chosen threshold: 204800 bytes/min (200 KB/min) — the shipped default, now
confirmed against real data rather than guessed.**

It sits between downloading (93.7) and gaming (289.5) with a 3.1× separation; the
geometric midpoint of those two is 165 KB/min, so 200 has margin on both sides.

### Cross-validation

Every figure was checked against `iwinfo assoclist` — mac80211's per-station byte
counters, which are wholly independent of netfilter and of the offload path.
Conntrack captured **95.5 %** of iwinfo's inbound bytes and 71–85 % of outbound.
The outbound gap is expected and is not an error: outbound is dominated by small
TCP ACKs, and iwinfo counts whole 802.11 frames where conntrack counts L3 payload.
The two move together, which is what matters.

### The download worry, resolved

This document previously warned that "byte rate cannot distinguish playing from
downloading" and that a background update would read as `up` and accrue time. On
this console that turns out **not** to be the case: during a 12 MB/min download the
outbound ACK stream was only 93.7 KB/min — less than a third of gameplay, and below
the threshold. A large download reads `down`.

The reason is that the metric is outbound-only. The earlier concern assumed the ACK
stream would be 1–2 % of a much larger downstream rate and would still clear any
sane threshold; measured, it is ~0.8 % and does not. Mitigations (a) and (b) below
are therefore not needed for this deployment.

### The measurement method matters — a naive sum does not work

Conntrack byte counters are per-flow and disappear when the flow expires, so a sum
over live flows is **not monotonic**. Measured live during this session, a naive
sum produced **−510.5 KB/min and −27.1 KB/min outbound during active gameplay**,
purely because the earlier download's flows aged out of the table between samples.

The helper must therefore keep a per-flow accumulator:

```
total += max(0, current_bytes - last_seen_bytes)   # for flows seen before
total += current_bytes                              # for flows seen for the first time
                                                    # vanished flows contribute nothing
```

keyed on conntrack id (`conntrack -L -o id`) where available, or on the 5-tuple
otherwise. Only the counter block belonging to the tuple whose `src=` is the console
counts as outbound.

## Re-calibrating later

Re-run the two `calibrate` commands above. The threshold is the only tunable;
nothing else in the driver needs to change. Counters reset when the router
reboots or the table is flushed — the driver notices the decrease, reports
`unknown` for that single tick, and re-baselines on the next one.
