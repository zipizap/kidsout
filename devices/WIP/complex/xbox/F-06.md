# F-06 — Instant-On standby must not burn the daily allowance

**Finding (REVIEW.1 §3, F-06).** v1 decided `up` from the number of concurrent
conntrack flows. The Xbox Series S ships with **Instant-On** as the default power
mode and holds persistent connections to Xbox Live while apparently switched off,
so a standby console clears any flow threshold. `engine.go` increments
`day.TUMinutes` on every tick where the state is `up`, so a console sitting in
standby all afternoon consumes the whole day's allowance and the kid arrives to
`blockedNoTime`. That is the most visible way this deployment could fail.

## What v2 measures instead

An nft counter on the router counts every forwarded frame whose **ethernet
source** is the console's MAC:

```
table inet kidsout {
        counter xbox_out { }                     # ether saddr <mac>
        counter xbox_in  { }                     # ip daddr <ipv4>   (diagnostics)
        chain accounting {
                type filter hook forward priority -150; policy accept;
                ether saddr <mac> counter name xbox_out
                ip daddr <ipv4>   counter name xbox_in
        }
}
```

`getState.sh` reads `xbox_out`, subtracts the previous reading, divides by the
elapsed time, and compares the resulting **bytes per minute** against
`device.json` → `state.threshold_bytes_per_min`.

Matching outbound on the MAC rather than the IP is what makes this work for IPv6
as well as IPv4. Inbound cannot be matched on the MAC — in the forward hook the
L2 destination is the router, not the console — so `xbox_in` is IPv4-only and is
recorded for diagnostics, not used for the up/down decision.

## Known limitation, stated plainly

Byte rate cannot distinguish **playing** from **downloading**. A background game
update in standby pulls tens of MB/min inbound, and the outbound ACK stream alone
(roughly 1–2 % of the downstream rate) is well above any threshold that a real
game session also clears. So a large background download will read as `up` and
will accrue time.

This is inherent to any traffic-based signal. The alternatives are worse: flow
counting (v1) is wrong in standby *without* any download at all, and there is no
console-side API to ask. If it turns out to matter in practice, the options are
(a) set the console to Energy-Saving power mode, which stops background downloads
while off, or (b) schedule updates into an hour the kid is asleep anyway.

## Calibration procedure

Requires the console present and the driver working (`./xbox.py selftest` green).

```
# 1. console in STANDBY (powered "off" but Instant-On), nobody touching it
./xbox.py calibrate --minutes 30 --interval 60 --label standby

# 2. console ACTIVELY in use — a game online, or a streaming app
./xbox.py calibrate --minutes 10 --interval 60 --label gaming

# 3. optional: console downloading a game update, nobody playing
./xbox.py calibrate --minutes 10 --interval 60 --label downloading
```

Samples are appended to `calibration.jsonl`. Each run prints
`n / min / median / max` in KB/min at the end.

Pick the threshold as: **comfortably above the standby maximum, comfortably below
the gaming minimum.** Geometric midpoint is a reasonable default:
`threshold ≈ sqrt(standby_max × gaming_min)`. Write it into `device.json` as
`state.threshold_bytes_per_min` (bytes, not KB).

If the two ranges overlap, the console is doing something in standby that looks
like use — check for a background download before lowering the threshold.

## Re-calibrating later

Re-run the two `calibrate` commands above. The threshold is the only tunable;
nothing else in the driver needs to change. Counters reset when the router
reboots or the table is flushed — the driver notices the decrease, reports
`unknown` for that single tick, and re-baselines on the next one.
